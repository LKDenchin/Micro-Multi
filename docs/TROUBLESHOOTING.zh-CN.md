# 常见问题

先看应用显示的错误，以及失败操作的工具记录。确认是哪一步出了问题，再调整相应配置，避免同时修改多项设置后无法判断原因。

## 模型连接失败

检查 API 地址是否为接口而非网页聊天地址，模型 ID 是否与供应商文档一致。认证失败通常需要核对密钥和账号权限；提示模型不存在时，应核对模型 ID。超时则检查服务连通性和配置中的请求超时。设置步骤见[模型配置](MODELS.zh-CN.md)。

Linux 无法保存密钥时，确认 Secret Service 凭据库已经运行并解锁。安装包包含应用运行时，系统凭据库仍由桌面环境提供。

## 团队没有开始执行

检查是否有待确认的方案卡片。成员只在你确认当前方案后启动；编辑方案或发送新任务后可能需要再次确认。还应查看是否有待处理的操作审批，或对话是否已暂停。具体阶段见[团队协作](AUTONOMOUS_COLLABORATION.zh-CN.md)。

若方案被修改，聊天卡片会原地显示最新分工，检查后再次确认即可，无需转到导图。提示正在保存时，等待规划轮结束后重试。已经启动的版本不能重复批准；需要新的任务时发送反馈，让主 Agent 提交新版方案。

## 插件较多时启动慢

聊天先恢复，插件客户端随后加载，最多三个并发。首次加载客户端可能需要构建，后续使用源码版本缓存。没有前端页面的插件不会因聊天页面探测而启动 Host；打开详情或调用功能时仍正常加载所需服务。

如果只有某个插件迟迟不可用，查看该插件的依赖和启动诊断。聊天可用和全部插件加载完成是两个时间点，原生插件实际服务激活仍取决于其依赖和初始化工作。

## 插件已安装，但没有可用工具

打开详情，检查是否启用、参数是否填写完整，并阅读依赖或启动诊断。使用 CLI 或远程服务的插件，还需确认程序、账号和凭据可用。只提供模型或界面组件的插件，不一定新增可调用工具。

源码包需要构建时，按应用提示检查构建方案。第三方包自身不完整或构建失败，需要根据报告处理相应依赖或构建问题后才能运行。安装流程见[原生插件](NATIVE_CORDIS.zh-CN.md)。

## 任务停止或测试失败

查看记录中的命令输出或模型错误，重做前对照对话检查项目文件。可以在原对话中要求解释失败，或验证未完成的部分。[恢复说明](DURABLE_TURNS_AND_MODEL_RECOVERY.zh-CN.md)介绍停止后保留哪些内容。

## 桌面应用或 AppImage 无法启动

检查端口是否可用、数据目录是否可写。Linux 还需满足凭据库和桌面库要求。Ubuntu AppImage 可能需要[桌面指南](DESKTOP_RELEASE.zh-CN.md#ubuntu-appimage-沙箱策略)中的应用专用命名空间策略；没有 FUSE 时使用 `--appimage-extract-and-run`。

报告问题时，提供应用版本、系统、操作、错误文字和最小复现步骤。脱敏日志可随 [Issue](https://github.com/LKDenchin/Micro-Multi/issues) 提交；漏洞和凭据应通过[安全政策](../SECURITY.zh-CN.md)中的私密渠道处理。
